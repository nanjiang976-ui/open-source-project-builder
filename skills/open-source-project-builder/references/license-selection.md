# 怎样带作者选许可证

从**待开源项目的根目录**开始。先判断作者是否已经选过，再决定这一轮是否需要问问题。许可证决定他人能怎样使用副本，仓库写入权限另由托管平台控制。未找到项目授权时，说明对外再利用通常需另获授权或有其他法律依据；GitHub 公开仓库仍依平台条款允许查看和 Fork。

## 先读项目已有的选择

查看根目录中的 `LICENSE`、`LICENCE`、`COPYING` 及带后缀的同类文件，并与 README、包清单的 `license`、相关 SPDX 声明对照。按文件内容和适用范围识别许可。工具自身的 MIT、`assets/licenses/` 中的备选模板、依赖或素材的版权声明只适用于各自的内容。

| 在项目里看到什么 | 怎样和作者继续 |
|---|---|
| 已有清楚的项目级许可证，包括自定义或双重许可 | 指出证据路径、名称和可确定的版本，用项目里的一个真实例子解释权利、义务和取舍，到此结束许可环节。Apache、GNU 等标准正文附录中的示例姓名和年份属于原文；已提供有效正文时，清单没有重复填写 SPDX 也不会产生新的选型决定。无需追问署名或是否补字段。多许可按原文解释可选项、须同时遵守的条件和各自的文件范围。 |
| README 或包清单已经明确声明许可，但根目录缺少正文 | 解释已选许可，指出只缺正式文本。需要落盘时只确认补齐的范围及必要署名。保留 SPDX 表达式中的 `OR`（任选）、`AND`（同时适用）和例外条件；补齐文本应覆盖整项声明。 |
| 正文为空、只是占位符、文件与声明冲突，或适用范围无法判定 | 列出具体证据，只问解决这处矛盾的问题。保留原件，等作者澄清后再提出补齐办法。 |
| 只有第三方许可，或没有项目级声明 | 指出查到的范围。引导或选型请求进入下一步；只读体检只说明现状和下一步。 |

遇到 `SEE LICENSE IN …` 先读所指文件。`NOASSERTION` 表示未作判断，`UNLICENSED` 可能是作者有意保留权利；确认对方是否打算开放授权，再继续。

## 用几道会改变结论的问题收敛

沿用作者已给的答案。先问最有区分度的一两项，再按回答追问。偏好仍会改变结论时，只解释不同答案意味着什么，等答案足以区分候选后再给首选。项目小、属于 CLI 或依赖用 MIT，都不能代替作者作决定。优先用情景代替条款名：

1. **别人把你的软件做成收费产品并分发时，可以闭源吗？** 如果可以，再问是否特别看重贡献者的明确专利授权，或明确禁止未经同意借作者名义宣传。表中的七种许可都允许商业使用；若要求禁止商用，说明与标准开源许可的区别，先厘清发布目标。
2. **哪些改动希望接收者拿到源码？** 想开放被修改的文件、允许闭源应用链接但保留替换库的能力，或希望分发的整个受覆盖衍生作品都遵守同类许可？项目形态可以帮助解释选项，最终以作者意图为准。
3. **如果服务商只在网上运行修改版，远程用户也应能取得对应源码吗？** 在网络服务可能改变结论时再问。若有已识别的第三方授权冲突、或代码及素材的授权人不明确，先厘清受影响的部分。

## 给出推荐和取舍

给一个首选，必要时给一个最接近的备选。把结论写成“根据你刚选的条件……；别人可以……；你和下游需要……；你接受的取舍是……”。说明义务在何时触发、源码给谁。可用下面的路径对照：

| 作者的目标 | 首选及关键取舍 |
|---|---|
| 宽松复用，倾向简短条款 | **MIT**。允许闭源商用，复制或分发实质性部分须保留版权及许可声明；下游通常无需分享其改进。 |
| 宽松复用，同时明确限制背书 | **BSD-3-Clause**。可闭源分发，须保留声明和免责条款；未经许可不得借版权人或贡献者名义宣传衍生产品。 |
| 宽松复用，重视明确的贡献者专利授权 | **Apache-2.0**。允许闭源，含有限范围的专利授权及其终止条件；再分发须保留许可、相关声明，并标注修改过的文件。 |
| 对受覆盖文件的改进要开放，允许独立文件闭源 | **MPL-2.0**。对外分发时，须让接收者取得受覆盖文件及修改的源码；独立文件可以使用其他许可。 |
| 闭源应用可以链接库，同时保留修改和替换该库的能力 | **LGPL v3**。分发修改的库与组合产品时，涉及库源码、声明及替换或重新链接等条件。 |
| 分发受覆盖衍生作品时，接收者应获得同样的自由 | **GPL v3**。分发受覆盖作品时沿用 GPL，分发二进制要依条款提供相应源码；仅内部使用通常不会触发分发义务。 |
| 修改后只提供网络服务，远程用户也能获得相应源码 | **AGPL v3**。除分发条件外，修改版支持网络交互时，应显著向与它远程交互的用户提供该版本相应源码。 |

推荐之后收口，例如：“按你的目标，我推荐 MIT。你接受别人可以闭源分发改版这个取舍吗？是否现在为项目创建 MIT 的 `LICENSE`？”允许作者比较、暂缓或只听解释。作者明确说“请生成 MIT 的 LICENSE”已经给出了选择和写入授权；如果仍缺必要信息，只问缺失项。对某项偏好说“同意”，不能自动解释为同意写文件。

## 确认后生成

- 落盘前核实具体版本、适用范围及模板需要的版权署名、年份。使用作者提供或已核实适用于该项目的公开信息。对于 GNU v3 系列，明确作者选择仅此版本还是此版本及后续版本，或沿用已有的明确声明。
- 从**本 Skill 安装目录**的 `assets/licenses/` 取得所选标准文本，按下表生成目标项目根目录的 `LICENSE`。逐字保留法律正文和第三方声明。署名属于待开源项目；此助手自身的 `LICENSE` 只授权助手本身。
- 写入前重新检查许可文件和当前工作区。采用只在文件不存在时创建的写法；若已出现文件，读取并改走“已有选择”分支。写后与模板比对，验证需要填写的字段、目录和版本，向作者报告创建路径和仍适用的第三方条件。只写本次授权的文件。

| 随包模板（相对于本说明） | 怎样使用 |
|---|---|
| [MIT](../assets/licenses/MIT.txt)、[BSD-3-Clause](../assets/licenses/BSD-3-Clause.txt) | 仅替换版权行的 `[year]` 和 `[fullname]`。确认版权行属于目标项目，且两处均已填妥。 |
| [Apache-2.0](../assets/licenses/Apache-2.0.txt)、[MPL-2.0](../assets/licenses/MPL-2.0.txt) | 原样复制完整正文。Apache 附录里的示范字段属于说明文本，应保留。 |
| [LGPL v3](../assets/licenses/LGPL-3.0.txt)、[GPL v3](../assets/licenses/GPL-3.0.txt)、[AGPL v3](../assets/licenses/AGPL-3.0.txt) | 写明作者选定的项目级 SPDX 标识（如 `GPL-3.0-only` 或 `GPL-3.0-or-later`）。若项目尚无此声明，可在 `LICENSE` 正文前单列一行项目适用声明，再原样附上标准文本。LGPL 模板已带完整 GPLv3；保留官方附录示范和许可文本作者的版权行。 |
