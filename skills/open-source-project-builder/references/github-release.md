# 带作者发布一个 GitHub Release

先判断作者想在哪一步得到帮助。“教我发版”时，默认在 GitHub 网页陪作者操作，每轮带到下一个能看见结果的节点。“只准备草稿文案”时，在聊天里交付可以粘贴的标题和正文。作者委托代操作时，区分本地提交、推送分支或标签、创建远程草稿和公开发布的授权；一组动作已经明确获准时，直接在该范围内继续。

## 1. 找到要交给读者的那一次提交

用项目里真实的一次改动解释三个词：**commit** 把当时的项目内容记成一个快照，**tag** 给其中某个快照起一个版本名，**Release** 给这个版本提供发行说明和下载入口。把代码推上 GitHub 后，还可以单独决定哪一个快照值得发给读者。

- 核对仓库、远程地址、工作区状态、预期版本号、已经验证的完整提交 SHA，以及该提交是否已推到目标仓库。未提交的修改不会出现在标签源码包里。还没有远端提交时，告诉作者缺哪一步；得到授权才提交或推送。
- 查项目版本文件、既有标签、Release（含可见草稿）、贡献或发版约定，以及 `.github/workflows/` 等实际发布入口。确认标签对应的提交，检查推标签或发布 Release 是否会触发构建、公开 Release 或分发到包仓库。先让作者知道会产生的实际结果。
- 首发沿用项目已选的版本。尚未定版本时，结合成熟度给出候选并问作者。更新版找**同一发布线**的上一相关标签，对照到本次提交的差异。已有同名草稿就打开草稿核对并接续；只有标签时，确认它确实指向目标提交。已有公开版本且对应提交正确时给出链接；标签指错时告知两个提交的差异，先讨论选择正确的标签或新版本号。查看不到私有草稿或请求超时，不能据此判断没有草稿。恢复操作前先核实远端现状。

## 2. 帮作者备好能直接粘贴的材料

给出具体的版本号、标签名、目标提交、正式版或预发布版、标题、发行说明和文件清单。每个附件注明它对应哪个版本、怎样验证。GitHub 会提供标签对应的源码 ZIP 和 tar.gz。纯文本 Skill 可让读者从源码包取出技能目录；桌面应用若承诺“一键安装”，就要从所选提交构建、试用并上传对应平台的安装包。[GitHub 的 Release 和源码归档](https://docs.github.com/zh/repositories/releasing-projects-on-github/about-releases)

- **首发文案**回答三件事：读者可以做什么、下载哪个文件并怎样第一次使用、有哪些已知限制。优先链接到该标签下的 README 或安装章节。
- **更新文案**给出比较起点，说明新功能、修复、兼容性变化和升级步骤。可用已合并 PR 生成初稿，再依提交和实际差异校对；直接推送且没有 PR 的改动也要纳入。[自动生成发行说明](https://docs.github.com/zh/repositories/releasing-projects-on-github/automatically-generated-release-notes)

## 3. 默认用网页，走到哪里就验到哪里

| 操作位置 | 这一步教什么 | 成功标志 |
|---|---|---|
| 仓库首页右侧 **Releases** → **Draft a new release** | 若已有该版本草稿，就在 Releases 中打开并编辑。在新表单里先核对仓库名。 | 面前是正确仓库及版本的编辑页。 |
| **Choose a tag** → 选已有标签，或输入新版本名并选 **Create new tag** | 新建标签时检查 **Target**，复核该分支当前指向的提交。若目标比当前分支尖端更早，或分支已前移，使用已核实指向目标的标签，或改用可明确指定完整 SHA 的路径。 | 拟发布的标签与验证过的提交一一对应。 |
| **Release title**、说明框、附件区域 | 粘贴第 2 步的材料；更新版可选 **Previous tag**。需要的安装包或其他资产在此上传。 | 标题、变化、下载说明和预期附件名一致，上传已完成。 |
| **This is a pre-release**、**Save draft**、**Publish release** | 测试版按需勾选预发布，读者仍可访问发布后的预发布页。**Save draft** 会把草稿存入目标仓库供有权限者继续编辑。点击 **Publish release** 会向该仓库的读者开放。使用不可变发行时尤其要在发布前备齐附件。 | 草稿能被维护者重新打开；公开发布后能打开对应版本的发行页。 |

找不到按钮、草稿或标签时，说明是仓库位置、账号写权限、标签规则还是还有信息待查。让作者在具体页面核对并回报所见的版本、提交或错误；收到结果后从原步骤接续。授权不足时仍可在聊天里交付文案和文件准备清单。[GitHub 网页发版步骤](https://docs.github.com/zh/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

**作者偏好命令行时**，先用 `gh release list --repo OWNER/REPO` 和 `gh release view TAG --repo OWNER/REPO` 查看当前状态。准备命令时把占位项换成已核实的实际值，指出它会写入哪个仓库。新建草稿时用 `gh release create TAG --repo OWNER/REPO --target FULL_SHA --draft --title TITLE --notes-file NOTES_FILE`；已有远端标签时把 `--target FULL_SHA` 换为 `--verify-tag`，并事先核对标签的提交。已有草稿使用编辑流程；作者明确授权发布该草稿后可用 `gh release edit TAG --repo OWNER/REPO --draft=false`。核对说明文件、附件和预发布设置后再执行相应写操作。[创建命令](https://cli.github.com/manual/gh_release_create) · [编辑命令](https://cli.github.com/manual/gh_release_edit)

## 4. 让读者完成第一次使用

公开后打开该仓库的 `/releases/tag/TAG`，核验标签实际指向的提交、预发布标记、版本说明和下载文件。从这个页面下载读者要用的文件，在干净目录按 README 完成第一项操作。记录公开地址、版本、提交、实际试过的文件和观察到的结果；只到草稿或缺少某个平台时，交代还未验证的部分。

最后用一句话复盘“这次为什么发、发了哪次提交、怎么知道读者能用”。作者想复用这套做法时，接到[提交与发版规则引导](commit-release-rules.md)，商定哪些选择值得写入该项目的 `AGENTS.md`。
