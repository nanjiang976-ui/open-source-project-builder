# 把提交与发版规则写进目标项目

让第一次维护开源项目的人能回答两件事：“这次改动怎样提交？”“哪一刻值得给读者发一个版本？”可以单独讨论，也可以在完成[第一次 GitHub Release](github-release.md)后，用刚做过的决定作为起点。

## 从已有做法开始

先定位作者正在维护的目标项目，检查工作区状态和项目根目录的 `AGENTS.md`。若仓库含多个子项目且本次发布对象不清楚，先核实范围。再按需查看 `CONTRIBUTING`、README、近期提交、已有标签和 Release、版本来源及发布工作流。普通目录也能讨论规则，把仓库建立后的操作写成约定即可。

向作者简述**已经确定的规则、观察到的习惯、这次需要决定的事**。例如，贡献指南明确要求 PR，就沿用并引用该文件；三条提交恰好用了英文，还不足以断定以后必须写英文。不同文件有实质矛盾时，点出各自路径与冲突点，先请作者决定哪条适用。若作者选的做法需要改工作流或贡献指南，把差异说明清楚，修改这些文件另依授权。

## 用下次真的会遇到的情形提问

每次只问能影响结果的未决问题，给出适合这个项目的建议并说明原因。作者已有答案就沿用。

| 情形 | 和维护者确定什么 |
|---|---|
| 今天同时修了一个错误，又改了一个无关示例 | 改动怎样拆成可审查的提交？标题用哪种语言和格式？直接提交、走分支还是提 PR？提交或合入前要运行哪些仓库里确实存在的检查？ |
| 有人等一个修复，另外几项新功能还在开发 | 哪些变化值得单独发版，哪些可攒到下一版？从项目的版本文件或已有标签出发，确定修复、新功能、不兼容变化怎么编号，何时用预发布版。 |
| 读者即将下载一版软件 | 谁确认目标提交、标签和公开时机？用户需要哪些附件和升级说明？发布前怎样验证，发布后谁用实际下载物走一遍？区分 Agent 可以准备的材料、可代办的操作以及维护者需要明确批准的动作。 |

一人项目可以从“一次提交解决一件事、标题说清变化、发版前跑一次已知检查、发版后试用下载包”开始。例如采用语义化版本的稳定库，`v1.2.0` 仅修复空输入错误时，候选版本可为 `v1.2.1`；是否立即发给用户仍由维护者决定。已有日期版本、中文描述或预发布约定也可沿用。[语义化版本](https://semver.org/lang/zh-CN/) · [约定式提交](https://www.conventionalcommits.org/zh-hans/v1.0.0/)

## 先给草稿，再合并

1. 展示**目标项目根目录下 `AGENTS.md` 的具体路径**和“提交与发版”小节的拟增改内容。用已确认的真实分支、检查命令和发布入口；尚未确定的建议留在对话里。有权威贡献指南时，用相对链接指过去，补充 Agent 应如何遵循即可。
2. 小节要短到作者愿意维护。比如已确认“中文描述、走 PR、`npm test`、只发源码包”的项目，可以写成下面这样。把示例中的每项替换为作者自己的决定。

   > **提交与发版**
   >
   > 每次提交集中处理一个问题，用中文写清改动。通过 PR 合入，合入前运行 `npm test`。
   >
   > 稳定版的兼容修复升补丁号，兼容新增升次版本号，破坏兼容性升主版本号。维护者选定发布提交和标签后，Agent 可以起草变更说明；公开前由维护者确认。
   >
   > 此项目使用 GitHub 标签对应的源码 ZIP。发布后，从 Release 页面下载该包，按 README 跑通首次使用步骤。

3. 作者只让讲解或看草稿时停在对话中。获得对目标和草稿的写入确认后，重新读取文件。已有等价规则则直接告知，无需修改；已有同义小节则就地合并；尚无文件时创建，尚无相关小节时追加。保留其他条款、格式和未提交改动。若新增内容与刚确认的草稿冲突，展示实际差异后再处理。
4. 回读并对照修改前后的文件，说明哪些约定已落盘、哪些外部文档被引用、再运行是否还有待处理内容。只改本次授权的项目文件。规则描述未来如何发布；写入小节本身不触发 commit、push、tag 或 Release。
