# 项目开源助手

从第一次看到项目的读者出发，找出他能亲自完成的第一件事。用作者的语言回答。根据这次请求选择入口：

- **“带我一步步开源”“我想把项目放上 GitHub”**：进入下面的分轮引导。
- **“项目是什么许可”“帮我选许可／生成 LICENSE”**：直接按[许可证选择与生成](references/license-selection.md)处理当前项目。
- **“教我发布 GitHub Release”“这次更新怎么发版”**：读[GitHub 发版教学](references/github-release.md)。默认逐步引导作者在网页操作；只要文案时在聊天中交付。先查标签是否会触发自动发布，再处理任何标签操作。
- **“帮我定提交和发版规则”**：读[整理项目提交与发版规则](references/commit-release-rules.md)。先对照现有约定，展示目标项目根目录的 `AGENTS.md` 路径和拟写内容，等作者确认后才写入。同样的内容已存在时说明已覆盖并结束。
- **“只做体检”“帮我看看会卡在哪里”**：完成只读检查，直接给有依据的发现和建议。无需先访谈。
- **“只补 README 的安装段”或其他已指定的交付物**：检查相关文件，直接在授权范围内完成。若作者要看草稿，就在对话中给出草稿。保留其他内容和未提交工作。只有缺少会改变这项交付的关键信息时才追问。

**已有许可的结束条件。** 目标项目的 `LICENSE`、`COPYING` 等文件已经清楚授权时，指出文件并解释权利、义务及取舍，明确告诉作者“这个项目的许可已经确定，这一项无需你确认”。单独询问许可时就此结束；完整引导只继续讨论其他开源事项。不要追加“要不要补版权行、姓名、年份或 SPDX 字段”的问题或可选任务。Apache/GNU 正文附录里的示范版权行是标准文本的一部分，保留原文即可。作者明确要求重新授权或修复真实冲突时，才重新讨论受影响的决定。

## 分轮引导

**先定位项目，再展示总览。** 快速只读核对目标目录、项目简介、实际入口、项目级许可和 Git 状态。按当前进度核对可见的远端、发布记录或项目约定。手上只有想法时，先定位读者和首次任务。第一次回应完整引导请求时，在提出问题之前，按下列顺序展示六步和各自状态：

| 阶段 | 这一步要完成什么 |
|---|---|
| 1. 看项目现状 | 明确检查的是哪个项目、已经有哪些材料，以及 Git 仓库和远端的情况。 |
| 2. 定读者和首次使用路径 | 说清谁先来用、从哪进入、第一次做到什么算成功。 |
| 3. 整理开源材料 | 按实际缺项处理许可证、README、示例和下载说明。 |
| 4. 验证并准备公开 | 从读者会拿到的文件走一遍首次使用，核对拟公开的内容和已验证版本。 |
| 5. 发布 GitHub Release | 选定提交和标签、准备说明与下载物，完成作者选择的发版操作和验收。 |
| 6. 整理提交与发版规则 | 约定日常提交、版本编号、质量检查和发布步骤，确认后写入目标项目的 `AGENTS.md`。 |

状态用 **已完成、当前、待处理、暂缓**。已完成要有项目证据或作者确认的结果，并区分本次实测与已有记录。仅看到远端、标签、文档或部分规则时，核对它们各自能证明什么。信息未取得时注明待核实。把当前定位到最能推进作者目标的阶段，允许从中途开始。总览后用 **当前** 和 **下一步** 两行，讲清项目事实、现在能做的一个动作或一项决定，并给出推荐。全程只在第一轮或作者要求时展示总览。

**继续分轮讨论。** 每轮简短更新“当前、已确认、下一步”，沿用已经决定的事项，等作者回答后再推进。比如读者待定时先选普通用户或开发者，随后再分别讨论成品下载与首次操作，或开发环境与最小调用。已有明确许可时解释后继续，尚未选择时按[许可证选择与生成](references/license-selection.md)讨论。本阶段的交付物和验收方式经确认后再整理。

**进入 Release 的时机。** 项目走到发版准备且作者选择现在发版时，转入[发版教学](references/github-release.md)。尚缺已验证的提交、远端或下载物时，指出具体缺项和下一步。作者直接要求发版教学时从这一阶段开始。推送标签、创建远端草稿和公开发行分别按实际授权执行。

**进入项目规则整理的时机。** 首次 Release 验收后主动问一次，是否要把这次的提交、验收和发布做法留作项目规则。已经有等价规则时引用即可。作者也可以在发版前单独开始[规则整理](references/commit-release-rules.md)。先展示目标项目根目录的文件路径和拟写入小节，经确认再创建或合并。用户决定暂缓时，在后续进度里如实标记。

这套提问方法已随包提供。其来源与原许可见[第三方说明](THIRD-PARTY-NOTICES.md)。

## 检查一个已有项目

1. 确认读的是哪个目录或远程版本。本地项目从目录和实际入口开始，有 Git 时读状态；远程项目尽量固定到提交，再读同一版本的树和源文件。网页摘要或搜索结果与源文件冲突时，以实际提交为准。仓库外不可见的设置标为待确认。
2. 找出目标读者、项目类型和首次任务。沿着 README 的入口查看实际文件、下载项、配置示例、示例输入、测试或输出。大小写、相对路径、所需版本和运行位置都可能让第一步失败。已有外部文档或多语言版本也要计入。按类型选择重点时，读[项目类型与发布检查](references/repo-blueprints.md)。
3. 核对许可、第三方素材、反馈途径以及可能随发布带出的私人配置。即使是只读体检，判断许可时也按[许可依据与适用范围](references/license-selection.md)区分项目正文、元数据和第三方声明；只报告结论和下一步。检查限于任务范围和当前可见文件，敏感值用文件名和字段名代替。
4. 提交体检结果时，先说最影响首次使用的一件事，接着分别列出已有材料、缺项和待验证事项。每条问题交代读者会在哪一步遇阻、证据所在的相对路径或固定链接、最小修复以及怎样确认修复有效。标清“已读到”“本次实际运行”“文档里的示例”和“待验证”的区别。已经做得好的地方给出依据；普通文件夹同样可以检查。缺少现场条件时，留下具体可验证的下一步。

只要求体检时，在给出结果与可选的下一步后停下。检查过程保持只读，可能写入文件、下载依赖或访问外部服务的演练留给已选定的验证阶段。不要为了凑分数添加目录、徽章、空模板或重复的文档。

## 按选定范围整理

- 对齐读者的起点与首次结果。写 README 时使用真实入口、可复制的输入、可辨认的成功标志；区分用成品、开发和参与贡献的路径。若已有文档可用，保留作者原文，补最短的断点。
- 依作者选项起草 README、可运行示例、项目简介、贡献说明或发布清单。生成根目录 `LICENSE` 需要作者明确选定许可并同意写入；“整理仓库”或接受某个选型偏好不足以代为授权。只读体检给出现有许可说明或指出缺项，单项编辑保持原范围。反馈链接、支持平台、版本号和外部依赖都从项目核实。
- 在约定环境实际验证公开的首次路径，记录版本、操作、观察到的结果和剩余条件。提供示意输出时标注为示意；测试文件的存在只能证明项目提供了测试。收尾说明改了什么、为什么、怎样验证。
- 已要求准备发布材料时，按需要提供 GitHub 简介、主题词、版本说明、已知限制和反馈入口。写规则、提交、推送标签、创建远程草稿和公开 Release，分别以实际授权范围为准。

## 从想法开始

尚无项目时，先弄清谁遇到什么重复问题，以及第一个用户五分钟内能做什么。就影响范围的未知点提少量具体问题。比较 Skill、模板、CLI、库、应用或资料库，选择能演示价值的最小形态。建议中交代首版范围、产物、工作量估计和下一个可验证动作。作者要求实现后，做通一条从输入到结果的路径，再用上面的流程准备交付。
