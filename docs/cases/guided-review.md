# 分轮引导怎样随作者的回答改变

2026 年 11 月 19 日在 Windows 上，用 Codex 桌面应用附带的后端做了四项行为验证。目标是看助手能否带第一次开源的作者做决定，同时尊重“只体检”和“只改一段”的明确请求。下面记录实际输入、结果和复查方法。

## 从 ZIP 安装一个 Skill

测试使用桌面包 `26.1111.9265.0` 附带的 `codex.exe 0.169.0-alpha.11.1`。只针对测试进程关闭其他技能，初始可用技能数为 0。解压新版候选 ZIP，把 `skills/open-source-project-builder` 整个复制到临时项目的 `.agents/skills/` 后，后端自动发现了 1 个项目级 Skill，解析错误为 0。唯一启用的就是项目开源助手。此次使用已有登录；个人安装和全局设置没有参与修改。

安装后从两条独立、只读的临时会话点名调用它。测试目录是普通文件夹，包含一个字符统计工具 WordCounter。成品是可在本地浏览器打开的 `dist/WordCounter.html`。源码一侧有 `package.json`、计数函数、构建脚本和测试。准备样例时，用 Node.js 24.14.1 运行了 `node build.mjs` 和 `node --test tests/count.test.mjs`，生成了 HTML，计数用例通过。这个小项目只用作验收样例。

## 同一个首问，两个不同的第二轮

两次都从 **“$open-source-project-builder 带我逐步开源这个项目。”** 开始。助手都从文件中找到了成品和源码，推荐先服务普通用户，也给作者留出了选择开发者的入口。以下是分别沿两个选择继续时得到的结果。

| 同一个项目里的作者答复 | 第二轮实际回复节选 | 作者接下来能决定什么 |
|---|---|---|
| “首版面向普通用户，优先让他们直接用上成品。” | “第二步，确认成品入口和第一次使用的成功标志。”助手给出 `你好ABC` 作为输入，预期结果为 `5`。 | 首次下载怎样拿到 HTML，以及什么结果算第一次操作成功。 |
| “首版面向开发者，优先让他们从源码入手。” | “第二轮确认开发者拿到源码后，第一次做到哪一步算成功？”它给出两条路径：构建并打开页面，或先验证计数逻辑。 | 是否把 `npm test`、`npm run build` 和打开生成的页面都纳入首次任务。 |

四个回合均完成。在这两次引导期间，项目内容和已安装 Skill 的文件清单与内容摘要前后一致。助手提出的 GitHub Release 附件是分发建议；浏览器页面显示的字符数是根据代码给出的预期。这两轮没有发布附件，也没有点击浏览器。

## 快捷入口是否尊重作者的范围？

另外两次 Windows 后端会话显式选择了从同一 ZIP 安装的 Skill，使用**有写权限**的两个相同项目副本。样例 LineCheck 带 README、Python 小工具、示例输入和维护笔记 `NOTES.md`。测试前后分别核对文件内容，便于发现越界编辑。上面的 WordCounter 测试单独验证了“只安装这一个 Skill”的条件。

| 请求 | 观察到的结果 | 实际核验 |
|---|---|---|
| 只做体检 | 助手直接指出“第一次运行”只有占位文字，引用 README、`linecheck.py` 和 `example.txt`，给出可用命令与预期输出。 | 全部 4 个项目文件的 SHA-256 前后一致。 |
| 只补 README 的“第一次运行” | 助手把占位文字换成在项目根运行 `python linecheck.py --input example.txt` 的说明，并给出实际输出 `2`。 | Python 3.12.10 运行该命令得到 `2`。目标段落前后的字节一致，其余 3 个文件逐份哈希相同。 |

## 怎样用自己的项目复核

选一个同时有成品和源码的项目，在两个新对话中发送相同的引导请求，分别选普通用户和开发者。核对第二轮的问题是否落在各自真实存在的入口上。再用一个项目副本分别尝试两个快捷入口，对照文件差异即可检查助手有没有遵守范围。同一类可核对的结果比逐字复现上表的措辞更重要。

此次覆盖桌面后端的技能发现、实际多轮回复和修改范围。真实新用户在桌面应用中手动完成安装、选择技能并独立读懂第一轮问题，仍需真人试用。[回到 README 看首次使用](../../README.md#first-run) · [首版只读体检记录](self-review.md)
