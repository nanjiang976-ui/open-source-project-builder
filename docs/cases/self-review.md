# 案例一：把只有三份文件的 Skill 交给第一次使用的人

版本说明：以下记录的是首次发布候选，当时的默认入口是只读体检。现在的默认入口为分轮引导，仍可点名只做体检。[当前版本的分轮验证](guided-review.md)

**第一次检查给出的答案是“读者会卡在安装”。** 这个结论来自新版助手对原始目录的实际只读检查。旧版已经说明了 Agent 要做什么，还列举了理想的仓库结构；第一次看到它的人却找不到从下载到首次调用的路径。本例记录作者的请求、检查时读到的证据、选定的修改以及 Windows 验证。

## 起点与请求

目标目录是原先安装的 `open-source-project-builder`。它有三份文件。运行检查的是工作区里新编写的同名 Skill，测试时明确指定新版 `SKILL.md` 路径和待检查的旧目录，避免同名条目混淆。

> $open-source-project-builder 我想把当前项目第一次公开到 GitHub。请先只读检查，告诉我一个第一次看到它的人会在哪一步卡住。请指出依据在哪个文件、最先该补什么，等我选定范围再整理。

独立执行者读完旧版全部三份文件，给出的首要发现如下。

> 第一次访问的人会卡在安装这一步。如果把当前目录原样放上 GitHub，读者看到项目名后，找不到一条从“拿到这些文件”走到“在 Codex 里用它检查自己的项目”的说明。

| 检查的实际文件 | 在旧版读到了什么 | 可以据此作出的判断 |
|---|---|---|
| `SKILL.md` | 从开源想法到首版的工作步骤，也要求项目提供 README 和快速开始说明。 | 已有 Agent 执行流程，但使用者无从知道怎样安装它。 |
| `agents/openai.yaml` | 原始默认请求是用英文请助手把一个开源想法整理成首版、目录和发布清单。 | 能服务有想法的作者；已有项目的读者还需一个合适的默认请求。 |
| `references/repo-blueprints.md` | 示范目录里写着 `README.md`、`LICENSE` 和示例文件。 | 磁盘清单证实这些只是示范。不能据此声称项目已经提供 README、示例或许可证。 |

为便于辨认此次输入，原版 `SKILL.md` 的 SHA-256 为 `FB5A9A7D788950ACAB760A75A2AED160220BE5EE44BE646E44105FC07994D3E9`。原版留在原安装位置，发布候选在单独目录整理。

## 作者选了哪些修改

作者选择中文首版，以 Windows Codex 为主入口；先只读检查，再按选定范围写文件。实际新增了面向读者的首页，写清技能目录、首次提问和预期结果。更新后的界面默认请求从检查当前项目开始，原有“从想法出发”的能力保留为第二入口。结构参考也增加了桌面工具、开发库、自部署应用和教程各自的首次成功标志。[成品 README](../../README.md) · [新版 Skill](../../skills/open-source-project-builder/SKILL.md) · [新版默认请求](../../skills/open-source-project-builder/agents/openai.yaml) · [项目类型参考](../../skills/open-source-project-builder/references/repo-blueprints.md)

这次预览验证时，作者把许可证选择留到首发，并通过分发渠道接收反馈。正式公开的版本现已采用 MIT，读者可以在仓库提交问题。[项目许可证](../../LICENSE) · [反馈入口](https://github.com/nanjiang976-ui/open-source-project-builder/issues)

## Windows 上实际验证了什么

2026 年 11 月 19 日使用 Windows Codex 桌面包 `26.1111.9265.0` 自带的后端 `0.169.0-alpha.11.1`。从测试程序调用同一后端的技能发现和会话接口，分别观察目录是否被发现、显式调用是否真的得到回答。旧版个人安装保留原样。

| 环节 | 做了什么 | 观察结果 |
|---|---|---|
| 技能格式 | 运行 Codex 的 `skill-creator/scripts/quick_validate.py`，检查新版 `SKILL.md`。 | 校验器返回 `Skill is valid!`。这项检查覆盖文件格式。 |
| 项目安装和自动发现 | 从没有 Git 的空白临时文件夹开始，将三个文件复制到项目的 `.agents/skills/open-source-project-builder/`，让桌面后端重新扫描。 | 新版条目从 0 个变为 1 个，范围为 `repo`，已启用，显示名为“项目开源助手”，解析错误为 0。这个项目位置使用了默认发现规则。 |
| 个人目录的隔离演练 | 在临时个人目录布局中复制同一包，逐一对照三个文件的 SHA-256。测试后端沿用 Windows 实际个人目录的定位，因此显式给该测试进程登记临时技能根。 | 三个文件逐字节一致。登记后新版被列为 `user`、已启用、路径正确。真实 Windows 个人目录原有的其他 Skill 也能被发现；此次没有往真实个人目录写入新版。 |
| 第一次真实调用 | 使用桌面后端正常已有的登录，建立只读临时会话。传入首次请求，并显式选中临时目录下新包的 `SKILL.md`，避免被旧同名版本替代。检查对象是仅含原版三个文件的副本。 | 会话完成，回复逐一点名三份文件，建议先补首次使用。检查前后，目标副本的相对路径与文件内容摘要一致。 |

实际会话中的两句回复是“**新读者最早会卡在首次调用之前。**”和“**最先建议只补根目录 `README.md` 的‘第一次使用’。**”它在检查结束时给作者两个可选范围，一是起草该段，二是先试装再写。会话记录中 5 个命令事件有 4 个成功、1 个失败；记录未保留该条命令的错误详情。关于三份文件和缺少首页的判断已与独立读取的目录及文件内容交叉核对。

本例验证了**打包的指令能被 Windows 上的 Codex 后端识别，并能完成一次真实诊断**。资源管理器点击、桌面对话框中的手动选择和首次开源者独立完成的体验尚未实测。若要做真人验收，让第一次使用的人只看 README，走到“能指出真实文件里的一个卡点，并知道怎样要求继续整理”即可。
